# C5 연대기 서사 강화 계획

> 기준 문서: [C5 일간 기록 원전 묶음](c5-daily-notes-source-packet-2026-08.md)  
> 대상: `presentations/c5-chronicle/index.html`  
> 상태: **계획 확정 전 / 아직 메인 미수정**

## 1. 이번 보강의 목적

기존 메인은 8/20 이후의 Design Pack·UX Preset·Markdown-first·Take 2의 논리를 잘 설명한다. 새 일간 기록은 그 논리가 갑자기 생긴 것이 아니라, 더 이른 기간의 계획·실패·토큰 제약·도구 재평가를 거쳐 나왔음을 보여 준다.

이번 보강은 이미지를 더 많이 붙이는 작업이 아니다. 다음 인과를 복원하는 작업이다.

```text
앱은 실험물, 목표는 조합 가능한 AI UX/UI 시스템
  ↓
단일 시스템 가설의 균열 / 시각 시스템 개선 실패
  ↓
플러그인·토큰 제약 / 문서와 리서치로의 전환
  ↓
게임 UX 흐름 문서 + Figma Make + A/B 테스트
  ↓
표현이 아니라 실제 작동을 묻는 UX 시스템 검증
  ↓
Markdown 계약 → HTML 투영 → Take 2
```

## 2. 반드시 바로잡을 사실

기존 메인의 `08.10 — 08.19 기록 공백` 장면은 제거하거나 완전히 대체한다. 이제 이 기간에는 사용자가 직접 제공한 일간 기록이 있다.

| 기존 표현 | 변경 |
|---|---|
| `C5 / 2026.08.10—08.26` | `C5 / 2026.08.04—08.26` |
| 8/10~19는 근거 없는 공백 | 8/4~9는 계획 주간, 8/10~14는 조합 가설·실패·자원 제약, 8/18~21은 Figma Make 검증 주간 |
| 8/20이 사실상 출발점 | 8/20은 “작동 여부”를 묻기 시작한 중간 전환점 |

8/15~17, 8/22~23은 실제로 공유된 기록이 없으므로, 빈 날짜를 꾸며 넣지 않는다.

## 3. 추가할 장면

### A. 프롤로그 — `앱보다 시스템이 먼저였다` / 8월 4~9일

- **서사:** 랜덤 비트 메이커는 최종 목적이 아니라, 조합 가능한 AI UX/UI 시스템을 시험할 실험물이었다.
- **보여 줄 것:** 최소 온보딩·직관 UI·확장된 AI 시스템이라는 초기 3개 목표.
- **형식:** 짧은 선언과 3개 가설 카드. 대형 이미지는 넣지 않는다.
- **근거:** 원전 문서의 직접 전사.

### B. 첫 막 — `한 시스템이 모든 것을 해결하지 않았다` / 8월 10~12일

- **서사:** 단일 시스템 가설은 캐릭터 팩 + UX/UI 시스템의 조합 가설로 바뀌었고, 새 디자인 시스템을 만들었지만 시각 작업의 느림과 개선 부재를 확인했다.
- **보여 줄 것:** `시스템 설계는 필연` → `실패`의 대비.
- **형식:** 한 줄짜리 판단 타임라인 + 접히는 실패 메모 2개.
- **근거:** 직접 전사. 원인을 새로 추정하지 않는다.

### C. 인터루드 — `토큰 0에서도 남는 일` / 8월 13~14일

- **서사:** 플러그인 경로가 멈췄을 때, 작업은 멈추지 않고 문서 읽기·HIG/UX 리서치·HTML↔Figma 변환 탐색으로 형태를 바꿨다.
- **보여 줄 것:** “첫 번째 실험은 실패했다”, “토큰이 0”, “토큰이 없으면 나는 무엇을 할 수 있는가?”
- **형식:** 일간 보드 스크린샷 2장을 작은 증거 프레임으로 사용하고, 옆에 `FAILED / RESEARCH CONTINUED` 상태 라벨.
- **주의:** 이 장면은 생산성 미화가 아니라 자원 제약 속 작업 방식의 전환으로 쓴다.

### D. 두 번째 막 — `Figma Make는 답이 아니라 시험대였다` / 8월 18~21일

- **서사:** 게임 UX 흐름을 정의하는 문서에서 시작해, Figma Make·레퍼런스·A/B 테스트를 거쳤다. 그러나 질문은 “만들 수 있는가?”에서 “UX 시스템으로 실제 작동하는가?”로 강해졌다.
- **보여 줄 것:** 기존의 Figma Make Overview / Adapter Reference, 그리고 일간 보드의 `문서 → Figma Make → A/B 테스트` 흐름.
- **형식:** 현재 `Figma Make` 장면을 8/18~21 범위로 확장. 단일 스크린샷 대신 3단계 process strip을 추가한다.
- **핵심 문장:** `Figma Make는 강한 출발점을 보여 줬다. 그러나 출발점은 검증이 아니다.`

### E. 기존 8/20~26 장면의 문장 보정

| 기존 장면 | 보강할 맥락 |
|---|---|
| 첫 반증 / 테마만 바뀐 어댑터 | 이미 8/10~12에 ‘시각 개선 부재’를 경험했기에, 8/20의 반증은 첫 실패가 아니라 **구조적 원인까지 선명해진 실패**다. |
| 프리셋 재정의 | Figma Make와 A/B 테스트를 거치며 “다르게 보임”과 “다르게 결정함”을 구분하게 됐다는 연결을 한 문장으로 보강한다. |
| Markdown-first | 8/13~14의 문서·리서치 전환과 연결한다. Markdown은 문서 지옥을 늘리기 위한 결과가 아니라, 정본을 고정하려는 응답이었다. |
| Take 2 | 8/24~26의 `가능성 → 망한걸까? → 첫걸음`을 짧은 리듬으로 넣어, Take 2를 최종 승리가 아닌 다음 실험의 시작으로 만든다. |

### F. 증거 아카이브의 역할 명확화

현재의 `결과물 수는 결론의 수가 아니다` 섹션은 유지한다. 문장만 다음처럼 강화한다.

- 25개 Figma 시스템 = 관찰 가능한 시각 언어와 편집 가능한 원본
- 32개 HTML = 실제로 렌더된 투영 결과
- 118개 기존 원본/감사 자산 = 비교와 반증의 자료
- 175개 전체 = 성공 개수가 아니라 **주장 강도를 조절하는 비교 표면**

### 기존 자산과의 역할 분담

- **Figma Make 화면:** 가능성과 관찰 범위
- **USPS / Industrial Swiss / Royal Mail 감사 화면:** 반증과 회복
- **Rasterline / Take 2 화면:** 문서 계약이 실제 표현으로 이어진 결과
- **Figma 시스템·HTML 아카이브:** 비교 가능한 결과군, 최종 성공의 증거 아님

## 5. 인터랙션 계획

1. 좌측 레일을 `8/04 계획 → 8/10 조합 → 8/13 제약 → 8/18 Figma Make → 8/20 반증 → 8/21 프리셋 → 8/24 계약 → 8/26 Take 2`로 재구성한다.
2. 새 초기 장면은 과도한 스크롤 길이를 피하기 위해, 한 장면당 핵심 판단 하나와 이미지 1~2개만 둔다.
3. 일간 보드 이미지는 클릭 시 원본 전체를 lightbox로 열고, 본문에는 읽을 수 있는 크롭과 텍스트 전사를 함께 둔다.
4. 실패 카드에는 새 실패를 중복 추가하지 않는다. 초기 실패는 시간축의 장면으로, 기존 카드들은 ‘규칙으로 회수된 실패’로 유지한다.
5. 아카이브 링크는 각 새 장면에서 한 번만 제공하고, 독자가 이미지 개수보다 증거 범주를 이해하게 한다.

## 6. 구현 순서와 검증

1. 일간 보드 원본을 프로젝트 자산 폴더에 복사하고, 파일명·출처·날짜를 manifest로 기록한다.
2. `index.html`의 날짜 범위·기록 공백 장면·좌측 레일을 교체한다.
3. A~D 장면을 추가하고, E의 기존 문장을 보정한다.
4. 모바일과 데스크톱에서 새 장면의 이미지 가독성·레일 순서·lightbox를 확인한다.
5. 메인에 쓰는 새 사실을 원전 문서와 대조하고, `OBSERVED / BUILT / CHECKED / OPEN / REJECTED` 라벨을 다시 점검한다.
6. 아카이브 총수 175, 자산 경로, 이미지 로딩 실패 0을 정적·브라우저 렌더 양쪽에서 검증한다.

## 7. 완료 기준

- 기존의 사실과 충돌하는 `8/10~19 기록 공백` 문구가 사라진다.
- 초기 계획·실패·제약·Figma Make 검증이 8/20 이후의 판단으로 자연스럽게 이어진다.
- 새 일간 이미지가 장식이 아니라 각 장면의 주장에 직접 대응한다.
- 이미지가 많아져도 “175개 = 175번의 성공”으로 읽히지 않는다.
- 모바일에서도 모든 새 캡처가 맥락과 함께 읽힌다.

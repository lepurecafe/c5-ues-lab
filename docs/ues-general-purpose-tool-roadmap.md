## 1. 프로젝트의 목표

**사람의 목표와 상황을 한 번 정의하고, 경험의 의미와 시각적 개성을 유지하면서 여러 매체·도구·결과물로 제작하고 수정할 수 있게 한다.**

여기서 재사용할 것은 색상이나 화면 모양만이 아니다. 누가 무엇을 하려는지, 어떤 정보가 먼저 필요한지, 선택·실패·복구가 어떤 의미인지, 어떤 표현이 제품에 어울리는지, 수정하면 무엇을 다시 확인해야 하는지를 함께 다룬다.

[UES 정본](04-universal-experience-system.md)의 §0·§1·§5·§6·§15에 이 목표가 이미 선언되어 있다. Take 2는 폐기된 실험 계획이며 현재 시스템 검증의 기준선이 아니다. COMMON SURFACE, 제품 소개 웹·접지물, 브랜드·굿즈 등의 과거 실험은 각자의 증거 한계 안에서 참고한다. 특정 앱 하나의 완성도로 전체 시스템의 성공 여부를 판단하면 목표가 좁아진다.

범용성의 의미는 **다양한 상황을 같은 기본 언어로 설명하면서도 상황에 필요한 차이를 보존하는 능력**이다. 처음부터 모든 출력 형식을 자동 생성한다는 뜻은 아니다.

### 목표 사용자는 두 부류다

| 사용자 | 달성해야 할 일 | 성공의 증거 |
| --- | --- | --- |
| 도구 사용자: BK, 기획자, 디자이너, 개발자, AI 작업자 | 입력 정리, 적합한 조합 선택, 결과물 제작, 변경·검증·인수인계 | 설명 없이 시작할 수 있고 수정 누락과 보정 시간이 줄어듦 |
| 결과물 사용자: 구매자, 독자, 학습자, 공연 진행자, 방문객 | 결과물이 제공하는 실제 과업 수행 | 목표 달성, 이해, 오류·복구, 매체별 접근성이 검증됨 |

예쁜 결과물은 첫 번째 사용자의 도구 사용성을 입증하지 않는다. 생성 시간이 짧아도 두 번째 사용자가 과업을 수행하지 못하면 성공으로 판단할 수 없다.

2026-09-11 기준 기존 main의 검사 결과는 Manifest PASS, Doctor `WARN 2 / PASS 2 / FAIL 0`, 회귀 테스트 PASS다. 94개는 **선택된 10개 Pack 문서에서 찾은 표식의 수**이며, 중복 제거된 결함·작업 94건이 아니다. 그중 36개가 영어 키워드로 분류된 런타임·접근성 표식이다. 전체 프로젝트의 미완료 작업 수나 완성률로 사용하지 않는다.

## 3. 범용 도구가 되기 위해 메워야 할 간격

### A. 무엇부터 할지 이해하기 어렵다

현재 [README](../README.md)는 규칙과 도구를 잘 연결하지만, 처음 온 사람이 자신의 목표에 맞는 최소 입력·추천 조합·완료 경로를 찾는 예시는 부족하다. 긴 정본부터 읽어야 한다면 범용 도구의 진입 비용이 높아진다.

**제안:** 첫 사용은 일상 언어로 6개만 입력한다. ① 누가 ② 어떤 상황에서 ③ 무엇을 끝내야 하는가 ④ 성공을 어떻게 확인하는가 ⑤ 제약은 무엇인가 ⑥ 어떤 결과물이 필요한가. 그다음 필요한 경우에만 데이터·권한·접근성·생산 조건을 추가한다. 질문에 답하지 못한 항목은 가정과 미결정으로 보여준다.

예: “처음 온 방문객이 소음이 큰 행사장에서 부스를 찾게 한다. 모바일 안내와 A4 안내물이 필요하다. 색 구분 없이도 읽혀야 한다.” 도구는 길찾기 구조·정보 우선순위·매체 손실을 제안하고, 사용자가 확인한 뒤 구체적인 Composition으로 확정한다.

### B. 출력 가능한 범위와 준비 수준을 고르기 어렵다

정본에는 8개 매체 계열이 있지만, 공통 Adapter Registry와 구현·검증 상태 목록은 없다. [생성기](../scripts/generate-c5-manifest.mjs)는 Pack/Preset을 등록한다. 실험별 Product Binding·Composition·로컬 Pack·로컬 Preset은 Manifest에서 탐색할 수 없다.

**제안:** 결과물 선택표와 예제 중심의 Recipe 목록을 만든다. Recipe는 특정 목표에 맞춘 시작 조합이며 Core 의미를 새로 정의하지 않는다. 각 선택지에는 `정의됨 / 예제 있음 / 생성 가능 / 실제 환경 확인 / 사용자 확인`을 표시한다. 미지원 항목도 “불가능” 대신 빠진 Adapter와 필요한 검증을 알려준다.

Binding이 없다는 뜻은 아니다. 정본 §7.1의 `c5.random-beat-maker`, 실험의 `binding.battle-beat-randomizer@1.1.0`, [최소 음악 앱](../experiments/take2-random-music-pipeline-2026-08-26/docs/composition-and-binding.md)의 `binding.take2.random-music.minimal@0.1.0` 등은 적용 목적이 다르므로 이름만 보고 합치지 않는다. 마지막 Binding은 진행자와 취미 청취자를 함께 다루며 환경 우선순위를 아직 분리하지 않았다. 등록할 때 별칭·파생·대체 관계를 확인한다.

### C. 문서 계약과 실행 검사의 범위가 다르다 — 입력 신뢰성 P0 구현됨

최초 감사 시점의 [Doctor](../scripts/c5-doctor.mjs)는 JSON Schema 기반 구조 검증기나 상태 전이 검증기가 아니었다. 2026-09-11 P0 수정 전 임시 fixture에 `{}`만 넣고 단독 실행했을 때 `status: pass`, `Manifest undefined`, 검사 문서 `0개`가 출력됐다. 필수 규칙과 배열이 없으면 빈 기본값으로 넘어갔기 때문이다. 당시에도 CI의 선행 Manifest drift 검사는 이 변경을 거부했지만 Doctor 단독 사용자는 잘못된 성공을 받을 수 있었다.

위 빈 입력 PASS는 후속 P0에서 수정했다. 버전 있는 외부 입력 계약, 필수 필드·타입·빈 Registry·검사 경로 검사, NOT_RUN, FAIL 시 포괄 PASS 억제가 구현됐다. [구현 기록](p0-reliability-hardening.md)을 현재 기준으로 사용한다. OPEN 탐지는 여전히 Pack 정본과 일부 파일명 규칙에 한정되고, 링크 검사는 `README / docs / design-packs / ux-presets`에 한정된다. 실험·발표의 전체 의존성과 HTML 내부 링크, Markdown 앵커·reference-style 링크는 이번 P0 범위가 아니다.

**제안:** 검사 규칙은 검사 대상 Manifest 바깥의 버전 있는 Schema에 둔다. 최상위 형식·필수 필드·허용 타입·빈 Registry·누락된 검사 경로부터 검증하고, `검사 안 함`을 PASS와 구분한다. 구조→ID 참조→상태 전이→매체 호환성→증거 연결 순서로 검사 범위를 늘린다. 실패한 상위 검사 뒤에 포괄적인 `OK_MANIFEST_VALID`가 나오지 않게 한다.

### D. 한 번의 수정이 여러 결과물로 안전하게 전달되지 않는다

[폐기된 Take 2의 당시 판정 §2·§5](../experiments/design-system-value-validation-2026-08-25/take-2-random-music-app/10-system-validity-verdict.md)에는 변경 영향 분석에서 Low-fi가 누락된 교훈이 남아 있다. 이는 새 도구의 요구사항을 생각할 때 참고하는 역사 기록이지 해당 실험을 재개하거나 현재 재사용 효과를 입증하는 근거가 아니다.

**제안:** Composition을 중심으로 source version/hash, 출력 파일, 의미 ID, 수정 담당 영역, 검증 기록을 연결한다. 변경 시 영향을 받는 출력과 무효가 된 증거를 먼저 보여준다. 사람이 수정한 영역은 보존하고, 소유권이 겹치면 덮어쓰기 대신 diff로 확인한다. 최초 생성보다 **다시 생성했을 때 수작업이 살아 있는가**가 핵심이다.

### E. 품질 점수·현재 상태·출시 가능성을 혼동하기 쉽다

최초 감사에서 서로 다른 수준의 PASS와 요약 불일치를 발견했다. 아래 R3/R4 항목은 **수정 전 발견 기록**이며 P0 후속 수정에서 revision·동일 분모 기준으로 정정했다.

- [Take 2 판정](../experiments/design-system-value-validation-2026-08-25/take-2-random-music-app/10-system-validity-verdict.md): Artifact Quality `92.4/100`, Pack strict `11/22`, Preset strict `3/6`; 생성물 품질과 시스템 준수 점수가 다름.
- [상위 결과표](../experiments/design-system-value-validation-2026-08-25/results/results-summary.md): `not started`인 반면 [R3 Composition](../experiments/design-system-value-validation-2026-08-25/r3/contracts/composition-manifest.md)에는 0.2.0 독립 재평가 결과가 존재. 같은 문서의 마지막 절에는 다시 `independent recheck pending`이 남아 있음.
- [R4 평가](../experiments/design-system-value-validation-2026-08-25/r4/01-evaluation.md): 공통 8항목 단순 평균은 `6.375→8.0`이다. 개선본 전용 두 항목까지 넣으면 `8.1`이 된다. 기록된 `6.2→8.1 / +1.9`를 같은 분모로 재현할 가중식은 문서에 없음.
- [1M Electric Composition](../experiments/bmw-1m-electric-launch/composition-manifest.md): `production`, `print-ready`, `gaps: []`와 실제 접지·양면 정렬·색상 proof 미검증이 공존. 문서상 출력 의도와 실제 생산 승인 상태를 분리할 필요가 있음.

**제안:** 결과는 점수 하나가 아니라 적용 범위·검사일·source revision·방법·판정·한계를 가진 Evidence로 저장한다. 요약은 최신 증거를 참조해 생성한다. 역사적 STOP은 보존하면서 후속 결과를 연결하고, 측정되지 않은 항목은 0점이나 PASS로 치환하지 않는다.

### F. 거래형 경험 밖으로의 확장이 필요하다

등록된 Reserve·Compare·Plan은 결정 중심 과업을 잘 설명한다. 학습·창작·읽기·실시간 제어·대화의 모든 순간을 “하나를 고르고 확정”에 맞추면 유용한 차이가 사라진다. 이미 [1M Electric 실험](../experiments/bmw-1m-electric-launch/composition-manifest.md)에 `launch.inform-consider@0.1.0-local`이 존재한다.

**제안:** 새 상황을 먼저 로컬 Recipe/Adapter로 표현한다. `learn.practice`, `create.iterate`, `inform.explore`, `operate.live`, `converse.resolve` 등은 후보 이름으로만 두고 독립 사례 두 개에서 반복되는 의무가 확인될 때 Preset 후보로 추출한다. 관찰·정보 전달만 있는 경험에는 커밋 불필요 사유와 이해·회상·길찾기 같은 실제 결과 증거를 선언한다.

## 4. 만들고 싶은 도구의 사용 흐름

| 단계 | 사용자가 보는 것 | 내부적으로 만들어지는 것 | 사용성 원칙 |
| --- | --- | --- | --- |
| 시작 | 만들 결과물과 사람의 목표, 샘플 선택 | 최소 Brief, 미결정 질문 | 전문 용어를 외우기 전에 시작 |
| 조합 | 추천 조합 1개와 대안, 추천 이유·지원 한계 | Binding + Preset + Pack + Adapter 선택 | 자동 추천은 수정 가능한 제안 |
| 구조 확인 | 흐름·콘텐츠 순서·상태·복구 | 의미 ID와 Composition | 결과물에 필요한 해상도만 노출 |
| 표현 확인 | 최소 구조와 최종 표현의 예시 | Low-fi/High-fi/매체 사양 | 레이아웃·밀도·타이포 차이까지 비교 |
| 제작 | 편집 가능한 출력과 미리보기 | 출력 파일 + dependency 목록 | 파일 소유권과 수정 지점 명시 |
| 수정 | 변경 대상·영향 결과물·재검사 항목 | source diff, 새 revision, stale evidence | 사람 수정 보존, 충돌은 표시 |
| 검증·전달 | 확인된 것·안 된 것·다음 행동 | Evidence와 Handoff 묶음 | 파일 존재와 실제 사용 성공을 구분 |

초기 인터페이스는 README의 시작 경로와 복사 가능한 Brief/Composition 예제, 소규모 실행 도구로 구현한다. 실제 제작자 관찰에서 반복 마찰이 확인된 뒤 선택·비교·영향 분석을 보여주는 Workbench를 검토한다. 이는 [MD-first 운영 가이드](../design-packs/00-md-first-experiment-workflow.md)의 단계적 제품화 원칙과 맞는다.

## 5. 다양한 상황과 결과물을 위한 확장표

아래는 지원 완료 목록이 아니라 목표와 검증 계획이다. 파일 형식뿐 아니라 그 매체에서 가능한 행동과 잃는 능력을 함께 명시한다.

| 상황 | 적합한 시작점 | 목표 결과물 | 반드시 보존할 의미 | 완료 증거 |
| --- | --- | --- | --- | --- |
| 거래·예약·비교 | 기존 Decision Preset | 웹·앱·서비스 안내 | 추천/선택/확정 구분, 실패·취소·재시도 | fixture + 실제 서비스 결과 수신 |
| 현장 운영·라이브 | 추후 별도 Binding, live 후보; Take 2 재사용 미승인 | 조작 화면·운영 큐시트 | 현재 상태, 다음 행동, 중단 비용, 대체 수단 | 기기 출력 + 방해 상황 복구 + 진행자 사용 |
| 브랜드·캠페인 | COMMON SURFACE Recipe | 웹·포장·광고·매장 안내 | 브랜드 개성, 동일 제품 사실, 변경·철회 범위 | 매체별 내용 일치 + 실제 출력·독해 |
| 학습·설명 | learn 후보 | 교재·발표·실습·퀴즈 | 선수지식, 진행, 피드백, 오답 복구 | 학습자 이해·과업 수행; 페이지 수가 아님 |
| 창작·편집 | create 후보 | 편집 화면·시안·창작물 | 탐색, 비교, undo, 버전, 저작 의도 | 수정·되돌리기·내보내기·재열기 |
| 읽기·정보 탐색 | inform 후보 | 보고서·편집물·포스터 | 읽는 순서, 근거, 개요/상세 전환 | 필요한 정보 찾기와 오독 검증 |
| 공간·행사·서비스 | Plan + 로컬 wayfinding/service | 안내판·동선·서비스 블루프린트 | 위치, 행위자, 순서, 인계, 대기·우회 | 거리·조명·혼잡·현장 동선 확인 |
| 대화·음성·AI | converse 후보 | 대화 스크립트·음성 흐름 | 기억, 불확실성, 확인, 중단·재개 | 실제 대화 과업·오인식·이관·청각 대안 |
| 모션·물리·복합 매체 | 매체 전용 Adapter 후보 | 모션 시퀀스·제어판·복합 경험 | 시간·피드백·감각 대안·동기화 | 재생·정지·물리 사용·대체 채널 검증 |

예를 들어 앱의 “다시 시도” 버튼은 포스터에 그대로 옮길 수 없다. 안내문·담당 창구·다른 경로처럼 같은 복구 목적을 달성할 표현으로 번역한다. 상태 없는 결과물의 불필요한 동작은 적용 제외 사유를 남긴다.

## 6. 최소 운영 구조 제안

Markdown은 사람이 수정하는 정본으로 유지한다. 기계가 읽을 필드는 문서 안의 일관된 메타데이터/구조 블록으로 제한하고, JSON 색인은 생성한다. 같은 ID·버전·상태를 여러 파일에서 독립 관리하지 않는다.

| 단위 | 최소 추가 데이터 | 이유 |
| --- | --- | --- |
| Binding Registry | ID/version, canonical, 사용자·상황·목표, status, derived-from/alias | 실험별 Binding 발견과 맥락 구분 |
| Adapter Registry | input/output 계약, 지원 버전·능력, 손실·보상, evidence | 출력 형식 선택과 호환성 판단 |
| Recipe 목록 | 해결 과업, 최소 Brief, 추천 조합, 예제, 지원 한계 | 처음 쓰는 사람의 선택 비용 감소 |
| Composition | pinned IDs/versions, source hashes, outputs, override ownership | 변경 영향과 재현성 |
| Evidence | claim ID, artifact ID/hash, method/date, result, scope, limitations | 증거 최신성·범위 판단 |
| Handoff | 시작점, 재생성 방법, 편집 파일, 미결정, 다음 담당자 | 다른 사람·도구로 이전 |

검사 단계는 `format → references → semantics → capability → evidence`로 나눈다. structural PASS만 있는 조합에는 semantic/runtime PASS를 표시하지 않는다. 검사하지 않은 범위는 `NOT_RUN`, 불필요한 항목은 근거 있는 `NOT_APPLICABLE`, 승인된 예외는 담당자·사유·유효 범위와 함께 기록한다. 이 상태명은 신규 제안이며 기존 Evidence vocabulary와의 매핑을 정의한 뒤 도입한다.

각 단계는 독립적으로 검토 가능한 변경으로 진행한다. P0 두 항목은 후속 승인으로 구현했고, 나머지는 아직 미구현 후보이다.

| 순서 | 작업 | 선행 조건 | 완료 기준 |
| --- | --- | --- | --- |
| P0-1 완료 | Doctor 입력 검증 보강 | 없음 | [구현·회귀 결과](p0-reliability-hardening.md): 잘못된 입력/경로 FAIL, NOT_RUN, 정상 fixture 유지, 포괄 PASS 억제 |
| P0-2 완료 | 최신 결과 안내·평가 정합성 | 기존 증거 확인 | R3 revision·범위별 요약, R4 동일 8항목 재계산, UES §14·§15 정정; Take 2는 폐기 상태로 분리 |

## 8. 범용성을 검증할 실험 설계

### 8.1 순수한 재사용 비교

| 실험 | 고정 | 변경 | 확인할 것 |
| --- | --- | --- | --- |
| Pack 교체 | 동일 Binding·Preset·매체·콘텐츠·버전 | 표현 Pack | 개성 차이와 의미 보존을 함께 확인 |
| 도메인 이전 | 동일 검증 규칙·선택한 Pack·목표 계열 | Binding | 제품별 차이를 국소화할 수 있는가 |
| 매체 번역 | 동일 Binding·Preset·Pack 의도 | 웹→편집/인쇄→공간/서비스 | 잃은 기능과 대안, 읽기·행동 의미 보존 |
| 수정 재전파 | 기준 Composition과 사용자 수정 기록 | 하나의 정책·제품 사실·상태 규칙 | 영향 누락, stale 출력, 재검사 누락, 작업량 |
| 신규 목표 계열 | Core·작성 형식·검증 방식 | 학습 또는 창작 과업 | Decision Preset에 억지로 맞추지 않고 표현 가능 |

Take 2의 두 Binding 자료는 역사적 구분을 유지하되 현재 대조 실험이나 기준선에서 제외한다. COMMON SURFACE를 새 실험 기준선으로 쓸지, 어떤 신규 사례를 고를지도 추후 실험 설계에서 결정한다. 위 표는 선택 가능한 검증 방법의 제안이며 이번에 실행할 계획이 아니다.

### 8.2 도구 사용자 평가

아래는 추후 새 실험을 설계할 때 검토할 후보이며 참여자 모집·실행 계획이 아니다. 초기 소규모 형성평가로 제작자 3–5명을 제안하되 통계적 일반화를 위한 표본은 아니다. 처음 쓰는 사람과 숙련 사용자를 구분하고, 동등 난도의 두 과업을 기존 방식과 UES 방식으로 수행하는 설계를 고려한다. 과업·순서, 모델·입력 자산·품질 기준·제한 시간을 기록하고 첫 설정 시간과 반복 수정 시간을 분리한다.

과업: 최소 Brief 작성 → 추천 조합 확인 → 두 형식 출력 → 사실 하나 변경 → 영향 확인·재생성 → 인수인계. 오류·도움 요청·중단·미완료도 기록하고, 완성된 사례만 평균 내지 않는다.

| 지표 | 측정 방법 | 초기 판정 기준 제안 |
| --- | --- | --- |
| 첫 유효 Composition까지 시간 | 시작~필수 입력·참조 검사 성공 | 15분 이내를 가설로 평가; 학습 시간을 별도 기록 |
| 자력 과업 완료 | 도움 없이 완료한 사람 / 참여자 | 80% 이상 목표; 소표본의 인원수도 함께 표시 |
| 의미 보존 | 사전 고정한 필수 의무 중 충족 수 | 적용 필수 의무 100%; 미적용 사유는 별도 |
| 변경 누락 | 영향 출력 중 미수정·미검사 출력 수 | 0; Low-fi·출력 원본·미리보기를 모두 포함 |
| 반복 수정 비용 | UES/기존 방식의 작업·보정 시간과 결함 | 동일 품질에서 중앙값 20% 감소를 가설로 확인 |
| 재사용 | 사전 정의한 재사용 가능 계약 단위의 실제 재사용 수 | 줄 수·파일 잔존율을 공식 재사용률로 대체하지 않음 |
| 인수인계 | 다른 제작자가 출력 재생성·수정 지점 식별 | 누락 입력 0, 수동 편집 손실 0 |
| 결과물 사용자 성과 | 목표별 이해·완료·오류·복구 관찰 | Binding별 기준을 사전 정의; 제작자 점수와 분리 |

15분·80%·20%는 관측 결과나 검증된 기준이 아니다. 첫 파일럿 전 확정하고, 변경 시 다음 실험부터 적용한다. 접근성·의미·권한의 필수 결함이 남으면 평균 점수가 높아도 승격하지 않는다.

## 9. 이번 작업과 다음 작업의 경계

최초 작업은 목표·현황·개선안 문서화, Draft PR #1 검토, Graphify 갱신이었다. 후속 사용자 승인으로 P0 Doctor 입력 검증·결과 요약 정합성을 수정하고 Take 2 폐기를 반영했다. [P0 기록](p0-reliability-hardening.md)이 현재 상태다. 새 Preset·범용 CLI·Workbench 구현이나 새 실험 설계·실행은 하지 않았다.

PR의 결과와 정확한 SHA는 [검토 기록](pr-1-review-2026-09-11.md), 그래프의 범위·생성 결과·한계는 [Graphify 갱신 기록](graphify-refresh-2026-09-11.md)에서 확인한다. 그래프는 현재 정본·운영·대표 실험 관계를 탐색하는 파생물이며, 실기기·인쇄물·사용자 검증을 대체하지 않는다.

작업 분담: 메인 Codex가 목표 해석·코어/운영 코드 검사·PR 검토·계획 작성·결과 통합을 담당했다. 읽기 전용 explorer 1개가 실험 증거와 불일치를 찾았고, 메인이 핵심 원문을 다시 대조했다. Graphify 의미 추출은 기존 자료 3개 묶음과 신규 문서 보강 1개 묶음, 총 4개 에이전트에 배정했다. 문서 reviewer 1개가 목표 정합성과 표현을 검토했고, Binding 명칭 보정 후 차단 의견이 없었다. 전체 검증 수치와 결과 파일은 갱신 기록에 연결한다.

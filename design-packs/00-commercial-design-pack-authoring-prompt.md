# 상업용 Design Pack 작성 표준과 마스터 프롬프트

> 목적: Figma Make·웹사이트·앱·스크린샷·사진·인쇄물·브랜드 레퍼런스 등 어떤 입력이든 **재사용 가능한 Markdown Design Pack**으로 전환할 때, 시각적 인상만 보존하는 문서를 넘어 실제 상업 제품에 투영할 수 있는 표현·상태·접근성·운영 경계를 명세한다.
>
> 이 문서는 디자인의 ‘정답’을 강제하지 않는다. 제품 UX 계약을 대체하지 않고, 그 계약을 훼손하지 않는 표현 시스템을 만든다.

## 0. 핵심 원칙

1. **원본에 충실하되, 원본이 말하지 않은 사실은 발명하지 않는다.** 어떤 입력에서 관찰한 값과 구조는 기록하고, 제품 정책·실시간 데이터·권리·기술 구현은 `미확정` 또는 `외부 권한 필요`로 분리한다.
2. **토큰은 색상표가 아니라 의미 체계다.** 원시값(`blue-700`)과 역할값(`action-primary`, `status-info`)을 분리한다. 브랜드 색을 오류나 성공 의미에 자동으로 겸용하지 않는다.
3. **컴포넌트는 정지 화면이 아니라 상태 기계다.** 기본, hover, focus-visible, pressed, disabled, loading, empty, invalid, error, success를 필요한 범위에서 정의한다.
4. **예쁜 실패 화면은 복구가 아니다.** 입력 보존, 명확한 원인, 다음 행동, 재시도·취소·되돌리기, 위험 작업의 확인을 설계한다.
5. **접근성·반응형·현지화는 막판 QA 항목이 아니라 설계 입력이다.** 키보드, 비색상 단서, 읽기 순서, 축소 동작, 긴 문자열·번역문·날짜/수량 형식을 함께 명세한다.
6. **브랜드 레퍼런스는 사용 권한이 아니다.** 상표·로고·제품명·사진·전용 UI의 재사용 가능 여부는 별도 권한으로 확인한다. 문서에는 ‘영감/관찰’과 ‘사용 허가’를 혼동하지 않는다.
7. **10/10 Markdown은 10/10 출시 증거가 아니다.** 문서 완성도와 구현·실서비스 검증을 분리해 평가한다.

## 1. 입력원과 증거 등급

입력원은 동일하지 않다. Design Pack은 입력의 약점을 숨기지 않고, **무엇까지 말할 수 있는지**를 형식 안에 보존한다.

| 입력원 | 신뢰도 있게 추출 가능한 것 | 직접 알 수 없는 것 | 권장 보강 |
| --- | --- | --- | --- |
| Figma/디자인 파일 | 토큰, 레이아웃, 컴포넌트 구조, 명시된 variants | 실제 런타임 동작, 실데이터, 보조기술 동작 | 프로토타입·코드·테스트 기록 |
| 공개 웹사이트 | 렌더된 시각, 정보 위계, 관찰 가능한 흐름 | 내부 토큰, 숨은 상태, 정책·데이터 출처 | 다양한 화면 크기·상태 캡처, 공개 문서 |
| 네이티브/웹 앱 | 실제 상호작용, 일부 오류·회복·전환 | 코드 구조, 모든 권한/예외 상태 | 여러 계정·네트워크 조건의 관찰 기록 |
| 사진/스크린샷 | 분위기, 재질, 색·타입 인상, 단일 장면의 계층 | 상호작용, 정확한 수치, 반응형, 접근성 | 원본 해상도, 추가 각도/화면, 유사 사례 |
| 인쇄물/공간/제품 | 물성, 인쇄·재료·형태·거리감 | 디지털 상태·키보드·데이터 흐름 | 디지털 적용 가설을 `도출됨`으로 분리 |
| 브랜드 가이드/자산 | 승인된 브랜드 요소와 사용 조건 | 제품 UX, 서비스 정책 | 공식 사용 가이드와 제품 요구사항 |

사진 한 장에서 인터랙션을 ‘복원’할 수는 없다. 이 경우 Design Pack은 시각 문법에는 강할 수 있으나, 컴포넌트 상태와 흐름은 `미확정`으로 남기거나 **새 제품의 UX 계약**에서 별도로 공급받아야 한다.

### 증거 등급과 기록 방식

모든 핵심 규칙, 수치, 주장에는 아래 중 하나의 등급을 붙인다. 이 규칙 하나가 디자인팩의 환각과 누수를 크게 줄인다.

| 등급 | 뜻 | 기록 예 |
| --- | --- | --- |
| `관찰됨` | 제공된 파일, 화면, 사진, 코드, 공개 문서에서 직접 확인 | `--color-brand: #003189` |
| `도출됨` | 관찰을 구현 가능한 일반 규칙으로 번역 | `action-primary는 배경과 4.5:1 이상 대비를 목표로 한다` |
| `미확정` | 원본·요구사항에 근거가 없어 결정 불가 | `실제 배송 ETA의 갱신 주기: 미확정` |
| `외부 권한 필요` | 브랜드, 법무, 정책, 데이터 소유자가 결정 | `상표/로고 사용 권한`, `환불 정책` |
| `출시 검증 필요` | 브라우저·기기·보조기술·실데이터에서 확인해야 함 | `스크린리더 알림`, `결제 실패 후 재시도` |

관찰값은 출처를 함께 남긴다. 예: `관찰됨 — 웹사이트 주문 화면, 데스크톱 1440px, 2026-08-24` 또는 `관찰됨 — 제공 사진 IMG_0421, 촬영 조건 미상`. 캡처에서 읽을 수 없는 값은 정확한 숫자인 척 쓰지 않는다.

## 2. 시작 전 최소 입력

아래 입력이 없으면 문서는 만들 수 있어도 상업 배포 준비 문서라고 주장하지 않는다.

| 입력 | 필요한 이유 |
| --- | --- |
| 원본 링크/파일/사진, 관찰 범위, 확인일 | 출처와 변화 추적 |
| 대상 제품·플랫폼·주요 과업 | 디자인이 해결하는 맥락 고정 |
| 사용자와 접근 환경 | 글자 크기, 입력 방식, 보조기술 요구 |
| 브랜드 소유·사용 권한 범위 | 상표·로고·저작물 오용 방지 |
| 실제 데이터와 정책의 소유자 | 가격, 재고, 배송, 계정, 결제, 알림의 진실성 확보 |
| 지원 언어·국가·단위·날짜 규칙 | 현지화와 레이아웃 붕괴 방지 |
| Product Binding/UX Preset 또는 기존 UX 명세 | 상태, 검증, 확인, 복구 의미 보존 |

## 3. 작성 순서

1. **입력 등록**: 모든 링크·파일·사진·앱 버전·관찰 조건을 Source Register에 기록하고, 사용 권한/접근 조건도 함께 적는다.
2. **범위 선언**: 어떤 화면/컴포넌트/물성이 원본에 있었고 무엇이 없었는지 적는다.
3. **시각 문법 추출**: 색, 타입, 밀도, 격자, 모서리, 그림자, 질감, 아이콘, 사진/일러스트 방향을 `관찰됨`으로 정리한다.
4. **역할 토큰화**: 원시 토큰 → 의미 토큰 → 컴포넌트 토큰 순으로 연결한다.
5. **컴포넌트 계약화**: anatomy, variant, 크기, 상태, 콘텐츠 규칙, 인터랙션, 접근성, 금지 사용을 작성한다. 사진처럼 인터랙션이 없는 입력은 상태를 추정하지 않고 UX 계약에 연결한다.
6. **구성 레시피화**: 화면을 나열하는 대신 ‘어떤 과업에서 어떤 컴포넌트를 어떤 순서로 조합하는가’를 적는다.
7. **흐름과 회복 명세**: 정상 경로뿐 아니라 빈 상태, 입력 오류, 네트워크 지연/실패, 권한 거부, 중단·취소, 되돌리기를 적는다.
8. **매체 적응**: 넓은 화면/좁은 화면, 키보드, 터치, 인쇄/물리 매체가 있다면 각각의 불변 조건과 변형 조건을 적는다.
9. **경계와 검증 게이트**: 권리·정책·실데이터·성능·접근성의 미확정을 열거하고 출시 전 증거를 정의한다.

## 4. 정본 Markdown의 필수 구조

한 파일을 정본으로 둔다. 복잡도가 높아질 때만 보조 문서로 분리하되, 정본에서 각 문서의 책임과 링크를 명시한다.

```text
0. 메타데이터 · Source Register · 증거 등급 · 적용/비적용 범위
1. Visual Grammar (의도, 분위기, 밀도, 이미지·아이콘 문법)
2. Foundation (색·타입·spacing·grid·shape·elevation·motion 토큰)
3. Components (anatomy, variants, states, content, a11y, do/don't)
4. Composition Recipes (페이지가 아닌 과업별 조합 규칙)
5. Flows & Recovery (검증, 비동기, 오류, 취소, 되돌리기, 완료)
6. Responsive · Localization · Accessibility
7. Commercial Boundaries (권리, 데이터, 정책, 보안/개인정보 책임)
8. QA · Release Gate · Change Policy (문서 증거와 런타임 증거 분리)
9. Open Questions / Decision Log
```

### 혼합형 구조를 쓰는 기준

다음 중 둘 이상이면 `README.md + foundation.md + components.md + patterns-or-flows.md + canonical.md`의 혼합형을 권장한다.

- 컴포넌트가 12개 이상이거나 상태 표가 길다.
- 모바일/데스크톱/물리 매체 등 두 개 이상의 명시적 투영이 있다.
- 결제·배송·계정·운영 도구처럼 회복 흐름이 3개 이상이다.
- 실제 구현/QA 기록이 지속적으로 누적된다.

그 외에는 단일 정본 Markdown이 더 낫다. 파일 분리는 길이 자체가 아니라 **검색성·책임 분리·변경 빈도**를 위해서만 한다.

## 5. 상업 품질을 만드는 세부 계약

### Foundation

- 색상: raw scale, semantic role, surface/text/border/action/status를 구분한다. 상태를 색 하나로만 전달하지 않는다.
- 타이포그래피: family, fallback, size, line-height, weight, letter-spacing, 최소/최대 폭에서의 줄바꿈 원칙을 기록한다.
- 레이아웃: 콘텐츠 최대 폭, 열 수, gutter, 간격 단위, 밀도, breakpoint가 아니라 **재배치 조건**을 설명한다.
- 모션: 목적, duration/easing 범위, interrupt 가능 여부, `prefers-reduced-motion` 대안을 기록한다.

### Components

각 컴포넌트에 최소한 아래를 채운다.

| 항목 | 질문 |
| --- | --- |
| Anatomy | 필수/선택 슬롯은 무엇인가? |
| Variants & size | 어느 목적에 어떤 변형을 쓰는가? |
| State | 각 상태에서 보이는 단서와 가능한 행동은? |
| Content | 라벨 길이, 아이콘 단독 사용, 숫자/날짜 형식은? |
| Interaction | 클릭/탭/키보드/터치 때 무엇이 바뀌는가? |
| Accessibility | 이름, role, focus, 오류 연결, live update는? |
| Misuse | 위험하거나 혼동되는 사용은 무엇인가? |

필수로 점검할 상태: `default`, `hover`, `focus-visible`, `pressed`, `disabled`, `loading`, `empty`, `invalid`, `error`, `success`. 모든 컴포넌트에 모두 적용할 필요는 없지만, 적용하지 않는 상태도 이유를 남긴다.

### Flows, data, and recovery

- 입력값과 오류 메시지를 필드 단위로 연결하고, 사용자가 고친 값은 실패 후에도 보존한다.
- 로딩은 기다림의 이유·범위·다음 행동을 알려야 한다. 무한 spinner는 허용하지 않는다.
- 위험 작업은 대상, 결과, 취소 가능성, 확정 행동을 확인한다. 가능하면 되돌리기 기간과 방법을 명시한다.
- 가격, 재고, 도착 예정, 추적 상태, 계정 권한, 알림 수신 여부 같은 값에는 데이터 출처·마지막 갱신·오류 시 표현·사용자 행동을 정의한다.
- 빈 상태에는 ‘데이터 없음’의 원인과 시작/재시도/필터 해제 중 가능한 행동을 제시한다.

### Accessibility, localization, responsive

- WCAG 대비는 텍스트와 비텍스트 UI 모두 점검한다. 단, 문서의 수치만으로 실제 렌더링 대비를 통과했다고 주장하지 않는다.
- focus-visible은 항상 눈에 보이고, 키보드 순서는 시각 순서와 논리적으로 일치한다.
- 오류·성공·진행은 색 이외에 문자, 아이콘, 위치, ARIA/live announcement로 전달한다.
- 200% 확대와 긴 번역문에서 잘림·가로 스크롤·의미 역전이 없는지 출시 검증에 넣는다.
- 좁은 화면에서는 ‘축소’가 아니라 우선순위 재배치, 터치 대상, 고정 영역, 안전 영역을 명세한다.

### Commercial, legal, and operational boundaries

- 레퍼런스 브랜드의 상표, 로고, 도메인, 제품 사진, 고유 카피는 **관찰 대상**일 수 있지만 자동 재사용 대상이 아니다.
- 결제, 개인정보, 위치, 배송, 의료, 금융, 미성년자, 접근성 고지 등은 해당 조직의 법무·정책·보안 담당자의 승인 없이는 ‘준수’라고 표기하지 않는다.
- 지표·재고·가격·ETA·후기·사용자 기록은 예시 데이터인지 실데이터인지 명시한다.
- 실제 제품의 에러 코드, 고객센터 에스컬레이션, SLA, 보존/삭제 규칙은 제품 운영자가 제공할 때만 확정한다.

## 6. 10점 품질 루브릭

| 축 | 배점 | 10점 수준의 기준 |
| --- | ---: | --- |
| 원본 충실도와 출처 | 1.0 | 관찰 범위·출처·미확정이 명확하고 추정값을 사실처럼 쓰지 않음 |
| Foundation | 1.5 | raw/semantic/component 토큰과 타입·레이아웃·모션이 연결됨 |
| Components & states | 2.0 | 핵심 컴포넌트가 상태·콘텐츠·접근성·금지 사용까지 가짐 |
| Composition recipes | 1.0 | 화면 모음이 아닌 과업별 조합·위계·밀도 규칙이 있음 |
| Flow & recovery | 1.5 | 정상/빈/지연/실패/취소/완료와 데이터 진실성이 있음 |
| A11y · responsive · localization | 1.5 | 키보드·비색상·축소·번역·읽기 순서까지 검증 계획이 있음 |
| 상업/권리/운영 경계 | 0.75 | 권리·정책·개인정보·실데이터의 책임자가 구분됨 |
| QA·변경 관리 | 0.75 | 문서/런타임 증거, release gate, open question이 분리됨 |

**합계 9.0 이상**을 ‘상업 사용을 위한 문서 준비도’로 본다. 실제 출시 평가는 별도로 실제 기기, 보조기술, 성능, 실데이터, 권한, 법무 검토 증거가 있어야 한다.

## 7. 복사해서 쓰는 마스터 프롬프트

아래의 대괄호를 현재 작업의 사실로 채워 넣는다. 없는 정보는 채우지 말고 `미확정`으로 남긴다.

```md
당신은 상업 제품용 Design Pack 문서화 전문가다. 아래 입력원(Figma, 웹사이트, 앱, 사진, 인쇄물, 브랜드 가이드 등)의 시각 언어와 관찰 가능한 행동을 분석해, 재사용 가능한 Markdown Design Pack 정본을 작성하라.

## 입력
- 원본: [Figma URL / 웹사이트 URL / 앱 이름·버전 / 파일 / 스크린샷 / 사진 / 인쇄물]
- 분석 범위와 관찰 조건: [페이지/프레임/화면/물체, 기기·화면폭·로그인/네트워크 조건]
- 확인일과 버전: [YYYY-MM-DD, version]
- 대상 제품/플랫폼: [웹·iOS·운영도구·키오스크 등]
- 핵심 사용자 과업: [과업]
- 기존 UX 계약(Product Binding/UX Preset): [링크 또는 요약]
- 지원 언어/지역: [예: ko-KR, en-US]
- 브랜드 및 자산 사용 권한: [확정/미확정과 소유자]
- 알려진 정책·실데이터 제약: [가격/재고/계정/배송/개인정보 등]

## 절대 규칙
1. 입력에서 직접 확인한 사실만 `관찰됨`으로 쓰고, Source Register의 출처·관찰 조건을 붙인다.
2. 디자인적 일반화는 `도출됨`, 판단할 수 없는 것은 `미확정`, 권리·법무·정책·실데이터는 `외부 권한 필요`, 실제 구현 확인 항목은 `출시 검증 필요`로 표기한다.
3. 원본 브랜드의 상표, 로고, 제품명, 사진, 카피를 재사용 가능하다고 가정하지 않는다. ‘공식’, ‘준수’, ‘실시간’이라는 표현은 증거가 있을 때만 쓴다.
4. 기존 UX 계약의 상태, 검증, 확인, 취소, 복구 의미를 삭제하거나 시각 효과로 대체하지 않는다.
5. 색상·글꼴·간격만 나열하지 말고 raw token → semantic token → component token의 관계를 만든다.
6. 핵심 컴포넌트마다 anatomy, variants/size, default·hover·focus-visible·pressed·disabled·loading·empty·invalid·error·success 중 관련 상태, 콘텐츠 규칙, 인터랙션, 접근성, 금지 사용을 명세한다.
7. 정상 흐름뿐 아니라 입력 오류, 빈 상태, 지연, 실패, 권한 거부, 취소, 되돌리기, 완료 후 다음 행동을 명세한다. 입력값 보존과 데이터의 갱신/오류 표현을 포함한다.
8. 키보드, focus-visible, 비색상 단서, 보조기술 안내, 축소/긴 문자열/현지화, reduced motion을 포함한다.
9. 단일 Markdown 파일을 정본으로 작성한다. 복잡도가 높아 보조 문서가 필요하면 분리 대상과 각 문서 책임을 마지막에 제안하되, 정본의 핵심 규칙은 완결되게 유지한다.
10. 이 문서는 구현 코드나 법적 승인서가 아니다. 문서 품질과 런타임/법무 검증을 분리한다.

## 반드시 포함할 목차
0. 메타데이터 · Source Register · 증거 등급 · 적용/비적용 범위
1. Visual Grammar
2. Foundation (color, typography, spacing/grid, shape/elevation, motion)
3. Components
4. Composition Recipes
5. Flows & Recovery
6. Responsive · Localization · Accessibility
7. Commercial Boundaries (rights, data, policy, privacy/security authority)
8. QA · Release Gate · Change Policy
9. Open Questions / Decision Log

## 출력 품질 기준
- 수치를 지어내지 않는다. 읽을 수 없는 값은 ‘미확정’으로 남긴다.
- 각 중요 주장에 증거 등급을 붙인다.
- 추상적인 ‘깔끔함’, ‘프리미엄’, ‘직관적’ 대신 관찰 가능한 규칙과 검증 가능 조건을 쓴다.
- 마지막에 10점 루브릭 자체평가, 부족한 증거, 다음 확인 행동을 표로 제공한다.
```

## 8. 출시 전 검수 게이트

Markdown 완성 후 최소 다음을 분리해 확인한다.

- **문서 검수**: 링크/출처, 토큰 누락, 상태표, 권리/데이터 경계, 미확정 목록, 변경 이력.
- **시각 검수**: 원본과의 비교 캡처, 색·타입·밀도·계층, 작은 화면과 긴 텍스트.
- **상호작용 검수**: 키보드, focus, 입력 오류, 로딩, 실패 후 재시도, 취소/되돌리기.
- **보조기술 검수**: 이름·role·오류 연결·상태 알림을 실제 스크린리더로 확인.
- **운영 검수**: 실데이터 갱신, 권한/개인정보, 예외 처리, 고객 지원/에스컬레이션 경계.
- **권리 검수**: 상표·로고·이미지·폰트·카피·데이터의 사용 허가와 크레딧 확인.

## 9. 작성 금지 신호

- 원본에 없는 가격·재고·배송 ETA·사용자 통계·정책을 사실처럼 작성함
- `hover`만 있고 focus, disabled, loading, error, empty가 없음
- 색상만으로 오류·성공·선택 상태를 전달함
- ‘반응형’이라고 쓰고 어느 조건에서 무엇이 재배치되는지 없음
- 권한 확인 없이 특정 기업의 로고/제품명/자산을 ‘디자인팩 자산’으로 편입함
- Preview HTML의 정상 화면을 근거로 실제 서비스·접근성·결제·추적 기능이 작동한다고 주장함
- 열려 있는 결정이 문서 끝에 남지 않아 구현자가 추정해야 함
